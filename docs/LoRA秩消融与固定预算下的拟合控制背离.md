# LoRA 秩消融与固定预算下的拟合-控制背离

本阶段在 `vla` 环境完成一组核心消融：只改变 LoRA 秩（r=4 / r=8 / r=16），其余训练条件完全一致，观察对验证损失与闭环任务成功率的影响。所有数字来自容器 `wzh-ai` 的真实训练与评估日志，未做虚构。

## 1. 实验设计

### 1.1 为什么固定预算、只变秩

要孤立"秩"这一变量，必须固定其它所有因素：同一数据集、同一学习率、同一 seed、同一训练步数、同一评估协议。若沿用此前"跑到收敛"的做法，不同秩的收敛速度不同，比较的将是"秩 + 训练量"的混合效应，无法归因。

| 固定项 | 取值 |
| --- | --- |
| 数据集 | `vla_pushcube_finetune/hf_dataset` v1.0（train 4044 帧 / val 882 / test 858） |
| 学习率 / 裁剪 | 1e-4 / max_grad_norm=1.0 |
| batch / 累积 | 4 / 4（等效 16） |
| warmup / scheduler | 50 / linear |
| 训练步数 | max_steps=192（与此前全量训练的最优 checkpoint 步数对齐） |
| seed | 42 |
| 验证监控 | 前 128 帧子集，每 64 步评估，保留 eval_loss 最低权重 |
| 闭环评估 | 同一 `vla/eval/eval.py`，5 条标准指令 × 3 回合，最大 40 步，成功判据 < 0.03 m |

### 1.2 变化项：秩与缩放

| 组 | LoRA r | alpha | alpha/r | 可训练参数 | 占底座比例 |
| --- | --- | --- | --- | --- | --- |
| A | 4 | 8 | 2 | 2,097,152 | 0.0537% |
| B | 8 | 16 | 2 | 4,194,304 | 0.1075% |
| C | 16 | 32 | 2 | 8,388,608 | 0.2149% |

保持 `alpha/r=2` 恒定是为了把 LoRA 更新 `ΔW = (alpha/r)·BA` 的缩放因子固定，使三组差异只来自适配器的**容量**（矩阵秩），而不是更新幅度。这是秩消融的标准控制方式。

实现上给 `src/vla_finetune/train.py` 增加了 `--lora-rank` / `--lora-alpha` / `--max-steps` 命令行覆盖，三组共用同一份 `trainer_lora.yaml`，由 `src/vla_finetune/run_rank_ablation.sh` 串行执行，避免多进程抢占 GPU。

### 2.1 补充对照：学习率调度的影响

为定位"全 0"的成因，额外跑一组 r=8，其余与消融完全一致，仅把 scheduler 从 linear 改为 constant（记为 `rank8_constlr`，结果在 `results/vla_ablation/rank8_constlr/`）：

| 配置 | eval_loss | 闭环成功率 | 平均距离改善 |
| --- | --- | --- | --- |
| r=8, linear（消融组） | 2.0037 | 0/15 = 0.0 | -0.0782 m |
| r=8, constant（对照） | 2.0372 | **6/15 = 0.40** | **+0.0500 m** |

constant-lr 在 eval_loss 略高的情况下，闭环成功率反而从 0 提升到 0.40，其中 `slide the cube ahead to the red goal`、`push the block onto the red disc` 两条指令各 3/3 成功停靠。这说明对照制度下的瓶颈是**线性退火过早把学习率压到 0**，使短预算内策略尚未收敛，而不是秩不够。

## 3. 分析：拟合-控制背离

**观察 1：秩越大，离线拟合越好。** eval_loss 随秩单调下降（2.067 → 2.004 → 1.963），训练 loss 末值也单调下降（0.98 → 0.73 → 0.54）。更大的适配器容量确实更贴合训练集的动作 token 分布，与参数量随秩线性增长（2.1M → 4.2M → 8.4M）一致。

**观察 2：离线拟合更好并未转化为闭环成功率。** 三组闭环成功率均为 0/15；平均距离改善随秩增大反而**变差**（-0.0098 → -0.0782 → -0.0996 m），即秩越大越倾向于过冲（把方块推过目标）。分指令看，r=4 在 `push the cube to the red target` 上平均改善 +0.0900 m、在 `push the block onto the red disc` 上 +0.0552 m，是三组里唯一出现正向靠近的，但都未达到 0.03 m 的停靠判据。

**观察 3：0/15 的主因是学习率退火，不是秩。** 补充对照给出直接证据：同为 r=8、同为 192 步，仅把 linear 换成 constant，成功率从 0/15 跃升到 6/15（0.40），距离改善从 -0.078 m 转为 +0.050 m。此前完整 2520 步 schedule 下 r=8 的最优权重（step192, eval_loss=1.9890）也曾达到 3/15=0.20。两处证据共同表明：固定 192 步 + linear 已把学习率压到接近 0，属于"欠训练 + 过早退火"制度；闭环表现对 scheduler 的敏感度远高于对秩的敏感度。三组线性消融之间的 0/15 不可解读为"秩对成功率无影响"。

**观察 4：要在成功制度下比较秩，需固定 scheduler 后重做。** 本阶段提供的 constant-lr 对照只覆盖 r=8 一点，不足以给出"成功制度下 r=4/8/16 的成功率曲线"。这是明确的后续工作：在 constant（或足够长的 schedule）下重跑三组、按多个 checkpoint 评估，才能回答"秩对最终成功率的影响"这一完整问题。

> 边界：本消融的 0/15 只说明"在该固定预算与 linear 判据下未成功停靠"；constant-lr 对照的 6/15 也只说明"该制度下 r=8 能学会停靠"。两者都基于 5 条标准指令 ×3 回合、`randomize_start=False` 的固定场景，重复回合非独立泛化样本，不构成任务完全学会的结论。

## 4. 工程要点

- `train.py` 新增四个覆盖参数（`--lora-rank` / `--lora-alpha` / `--max-steps` / `--lr-scheduler`），改动局部且向后兼容，原全量训练命令不受影响。
- 消融 driver 串行执行三组，每组训练后立即用同一个 `eval.py` 评估，避免加载不同 adapter 时相互污染；constant-lr 对照复用同一 driver 逻辑，仅加调度器覆盖。
- 守护进程在全部完成后自动运行汇总脚本生成对比表与柱状图，减少人工介入。
- 三组训练共约 80 分钟，constant-lr 对照约 28 分钟；大 adapter 与优化器状态不入库，仅 JSON / 表格 / PNG 入库。
